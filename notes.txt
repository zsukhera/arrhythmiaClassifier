MIT-BIH EDA 27-9-2026
- what does a sample mean in our context ?
ECG is an electrical signal that has been digitally sampled
360 samples make up 1 second of ECG data
sample 0       → 0 seconds
sample 360     → 1 second
sample 720     → 2 seconds
sample 1800    → 5 seconds

instead of plotting in samples, we can also plot in samples
- data can also be held locally but can also be used from physionet itself, which is v nice.

- what format gives us what?
atr has expert annotations
dat has ECG samples
hea has metadeta -> signal length, channels, and sampling frequency etc

- detailed description of what is contained in hea format
the .hea file is a small plain text file (~5 lines). wfdb.rdheader() reads it and turns each value into an attribute.
raw 100.hea:
    100 2 360 650000
    100.dat 212 200 11 1024 995 -22131 0 MLII
    100.dat 212 200 11 1024 1011 20052 0 V5
    # 69 M 1085 1629 x1
    # Aldomet, Inderal
line 1 = record line: name, number of signals, fs, sig_len
each signal line = file, format, gain, resolution, adc zero, initial value, checksum, block size, lead name
lines starting with # = comments

record-level fields (whole recording):
record_name  = 100 -> matches the file names 100.hea, 100.dat, 100.atr
n_sig        = 2 -> number of channels
fs           = 360 -> sampling frequency in Hz (360 samples per second per channel)
sig_len      = 650000 -> samples per channel. 650000 / 360 ≈ 1805.6 s ≈ 30 minutes of ECG
counter_freq = None -> optional second clock for converting sample numbers to an external time base, not used
base_counter = None -> starting value of that counter, not used
base_time    = None -> time of day recording started, left out (anonymity)
base_date    = None -> date recording started, left out
comments     = patient info:
    '69 M 1085 1629 x1' -> 69 year old male. 1085 1629 x1 are old tape/recording reference codes, not relevant for analysis
    'Aldomet, Inderal'  -> medications. Aldomet (methyldopa) treats high blood pressure.
                           Inderal (propranolol) is a beta-blocker -> lowers heart rate and can change rhythm.
                           keep this in mind when looking at heart rate features for this record

signal arrays (all None with rdheader because it only reads the .hea, no samples):
p_signal   -> physical signal in mV, float array of shape (sig_len, n_sig). filled when using rdrecord
d_signal   -> digital signal, the raw integer ADC values stored in the .dat file
e_p_signal, e_d_signal -> "expanded" versions, only used when channels have different sampling rates

per-signal fields (one entry per channel -> [MLII, V5]):
sig_name        = ['MLII', 'V5'] -> lead names. MLII = modified limb lead II, the main lead in almost every
                  MIT-BIH record and the one usually used for beat classification. V5 = modified chest lead.
                  the second channel changes between records (usually V1, sometimes V2, V4, V5)
file_name       = ['100.dat', '100.dat'] -> both channels are in the same file, samples interleaved (ch0, ch1, ch0, ch1, ...)
fmt             = ['212', '212'] -> storage format. 212 = two 12-bit samples packed into 3 bytes
samps_per_frame = [1, 1] -> each channel is sampled at exactly fs (2 would mean twice the base rate)
skew            = [None, None] -> time offset to align channels, None = already aligned
byte_offset     = [None, None] -> bytes to skip at start of .dat before samples begin, None = start at byte 0
adc_gain        = [200.0, 200.0] -> 200 digital units = 1 mV
baseline        = [1024, 1024] -> digital value that corresponds to 0 mV
units           = ['mV', 'mV'] -> physical units
adc_res         = [11, 11] -> ADC resolution in bits. 2^11 = 2048 levels (0 to 2047)
adc_zero        = [1024, 1024] -> digital value at the middle of the ADC range (same as baseline here, but not always)
init_value      = [995, 1011] -> first sample's digital value per channel, used to check the file was read correctly
checksum        = [-22131, 20052] -> 16-bit sum of all samples per channel, detects corrupted/truncated .dat files
block_size      = [0, 0] -> 0 = data can be read as a plain continuous stream

how gain, baseline and digital values fit together:
physical (mV) = (digital - baseline) / adc_gain
first MLII sample: (995 - 1024) / 200 = -0.145 mV
first V5 sample:   (1011 - 1024) / 200 = -0.065 mV
full range: 0 to 2047 -> about -5.12 mV to +5.12 mV
rdrecord does this conversion to produce p_signal. wfdb.rdrecord(path, physical=False) gives the raw integers in d_signal instead.

- how do the 2 channels combine to form a single file? can i access the channels separately?
the samples are interleaved. the .dat file is one long stream of frames, each frame = one sample from each channel at the same moment:
    frame 0: [MLII s0][V5 s0]
    frame 1: [MLII s1][V5 s1]
    ...
    frame 649999
format 212 -> each sample is 12 bits, so one frame (2 samples) = 24 bits = 3 bytes, packed like this:
    byte 0: low 8 bits of MLII sample
    byte 1: high 4 bits of V5 sample | high 4 bits of MLII sample
    byte 2: low 8 bits of V5 sample
check: 100.dat is 1,950,000 bytes = 650,000 frames x 3 bytes, no header or padding (that's why byte_offset = None)
wfdb unpacks the bytes, splits them into columns and applies the gain/baseline conversion for us

yes, channels can be accessed separately:
1. slice the array (each column = one channel):
    mlii = record.p_signal[:, 0]
    v5   = record.p_signal[:, 1]
    mlii = record.p_signal[:, record.sig_name.index("MLII")]   # by name, safer since channel order varies between records
2. load only the channel you want:
    rec = wfdb.rdrecord("../datasets/mitbih/mitdb/100", channels=[0])            # by index
    rec = wfdb.rdrecord("../datasets/mitbih/mitdb/100", channel_names=["MLII"])  # by name (newer wfdb versions only)
    rec.p_signal.shape -> (650000, 1)
3. load only part of the recording:
    rec = wfdb.rdrecord("../datasets/mitbih/mitdb/100", channels=[0], sampfrom=0, sampto=3600)  # first 10 s
4. raw integers instead of mV:
    rec = wfdb.rdrecord("../datasets/mitbih/mitdb/100", channels=[0], physical=False)
    rec.d_signal -> the 12-bit values as stored in the file
MLII is the lead to use -> present in nearly every MIT-BIH record, the second channel changes between records.
so pick it by name (sig_name.index("MLII")) instead of hard-coding [:, 0]

- what is contained in the .atr
the .atr holds the cardiologists' annotations: one label for every beat, plus some extra marks (rhythm changes, noise).
it is a binary file. wfdb.rdann(path, "atr") reads it into an Annotation object, where every field is a list/array
with one entry per annotation. record 100 has 2274 annotations.

how it is stored on disk:
a list of 16-bit words. in each word, top 6 bits = annotation type code, bottom 10 bits = samples since the previous annotation.
    first word of 100.atr = 0x7012 -> code 28 ('+' rhythm change), 18 samples after the start
the positions are stored as gaps, so rdann adds them up to get absolute sample numbers.
a few special codes attach extra info to the previous annotation instead (e.g. code 63 = aux_note text follows)

fields:
record_name      = 100 -> which record the annotations belong to
extension        = atr -> the file extension that was read (atr = the reference annotations made by the cardiologists)
sample           = [18, 77, 370, 662, ...] -> where each annotation is, as a sample number.
                   for beats it sits on the R peak (the tall spike). time in seconds = sample / fs, e.g. 77 / 360 = 0.214 s
symbol           = ['+', 'N', 'N', ..., 'A', ...] -> the label. this is what the ML model will learn to predict
subtype          = only 0 or 1 -> extra sub-classification. in record 100 only one annotation (the single V beat, at sample 546792)
                   has subtype 1, the rest are 0. on noise marks ('~') it records which channels are noisy. can be ignored for beats
chan             = always 0 -> the channel the annotation refers to. every annotation is attached to channel 0,
                   it does not mean the beat is only visible on MLII
num              = always 0 -> spare number field, not used in MIT-BIH
aux_note         = ['(N\x00', '', '', ...] -> free text, almost always empty. on '+' annotations it holds the rhythm name.
                   the \x00 at the end is a null byte left over from how the text is stored, strip it before using
fs               = 360 -> sampling frequency, copied from the .hea so sample numbers can be turned into seconds
label_store      = None -> the numeric type codes as stored in the file. not kept by rdann by default, symbol is used instead
description      = None -> text meaning of each symbol, not filled by default.
                    wfdb.io.annotation.ann_label_table has the full symbol -> description table
custom_labels    = None -> for databases that define their own labels, MIT-BIH uses the standard ones
contained_labels = None -> summary of which labels appear in the file, not filled by default
ann_len          = 2274 -> number of annotations

what is in record 100:
    N: 2239 -> normal beat
    A: 33   -> atrial premature contraction (a beat that starts early in the atria)
    V: 1    -> premature ventricular contraction (an early beat starting in the ventricles)
    +: 1    -> rhythm change, aux_note = '(N' at 0.05 s -> normal sinus rhythm for the whole recording
not every annotation is a beat: 2274 annotations but 2273 beats, the '+' is not a heartbeat.
other non-beat symbols across the database: '~' signal quality change, '|' isolated artifact, '"' comment, 'x' blocked P-wave,
'[' and ']' start/end of ventricular flutter, '!' ventricular flutter wave. these must be filtered out before training.
the classes are very imbalanced (2239 N vs 1 V here), which the model will have to deal with

- what is contained in the .dat
the .dat is the ECG itself: just the samples, no labels and no description of its own.
without the .hea the bytes cannot be read (the header gives the format, number of channels, gain and baseline).
layout and format 212 packing are described above (see the 2 channels question).

what rdrecord gives back from it:
d_signal = raw ADC integers exactly as stored, shape (650000, 2), dtype int64 -> rdrecord(path, physical=False)
p_signal = the same samples converted to mV, shape (650000, 2), dtype float64 -> rdrecord(path), the default
    first 5 frames, digital: [995, 1011] repeated
    first 5 frames, mV:      [-0.145, -0.065] repeated
    (digital - baseline) / adc_gain gives exactly p_signal for every sample -> confirmed True

checks against the .hea, per channel:
MLII:
    init_value   = 995, .hea says 995 -> first sample matches
    checksum     = -22131, .hea says -22131 -> file is complete, not corrupted
    digital range = 481 to 1311 (ADC allows 0 to 2047) -> nowhere near the limits, so nothing was clipped
    mV range     = -2.715 to 1.435
    mean -0.306 mV, std 0.193 mV
V5:
    init_value   = 1011, .hea says 1011
    checksum     = 20052, .hea says 20052
    digital range = 531 to 1269 (ADC allows 0 to 2047) -> no clipping
    mV range     = -2.465 to 1.225
    mean -0.191 mV, std 0.148 mV

observations:
the mean is not 0 mV on either lead -> the signal sits below zero (a DC offset). ECGs also drift slowly over time
(baseline wander from breathing and movement), both should be removed with filtering before feature extraction.
checksum and init_value give a quick way to confirm every .dat file downloaded correctly.

## Dataset notes — EDA observations

### MIT-BIH file formats

- `.hea` — plain-text header: record name, number of signals, sampling frequency, signal length, per-channel gain/baseline/lead name.
- `.dat` — raw ECG samples (format 212: two 12-bit samples packed into 3 bytes, channels interleaved frame-by-frame).
- `.atr` — binary cardiologist annotations: one label per beat (R-peak sample position + symbol). Non-beat symbols (`+`, `~`, `|`, `"`, `x`, `[`, `]`, `!`) must be filtered before training.

Key facts for record 100:
- 2 channels: MLII and V5. MLII is the primary lead — present in nearly every MIT-BIH record; second channel varies (usually V1, V2, V4, V5) — **always pick MLII by name** (`sig_name.index("MLII")`), not hard-coded index 0.
- 650,000 samples per channel ≈ 30 minutes. fs = 360 Hz.
- Gain = 200 digital units/mV, baseline = 1024. mV range ≈ −5.12 to +5.12 mV.
- Mean signal is not 0 mV (DC offset + baseline wander from breathing/movement) → **remove with filtering before feature extraction**.
- Class imbalance is severe (record 100: 2239 N, 33 A, 1 V) — model must handle it.
- Medications (e.g. Inderal/propranolol) affect heart rate and rhythm for specific records — relevant context when interpreting per-record anomalies.

### MIT-BIH vs PTB-XL — key distinction

MIT-BIH is a **beat-level annotated arrhythmia dataset** (2-channel, 360 Hz, beat labels).  
PTB-XL is a **record-level clinical ECG dataset** (12-lead, 500 Hz, multilabel diagnostic superclasses).  
**Label spaces are incompatible — never conflate PTB-XL diagnostic superclasses with MIT-BIH beat-level arrhythmia classes.**

Universal features present in both datasets (for reference if cross-dataset work arises):
heart rate, RR mean/SD, QRS duration, QT, QTc, P/R/T amplitudes, QRS area/energy, T-wave energy, entropy, HRV features.

Features requiring multiple beats (HRV): SDNN, RMSSD, pNN50, Poincaré SD1/SD2, sample entropy.

PTB-XL has 12 leads (I, II, III, aVR, aVL, aVF, V1–V6); MIT-BIH has 2.  
**Current working decision: use Lead II only** when cross-dataset alignment is needed (Lead II is present in both).
